## Context

핀 상세 페이지의 연관 핀 API(`GET /api/pins/{id}/related`)는 현재 태그 기반 매칭만 수행한다. 핀의 태그를 조회한 뒤, 태그가 0개이면 즉시 빈 배열을 반환한다. 태그가 있더라도 겹치는 핀이 없으면 역시 빈 결과다.

프론트엔드는 API 에러를 catch 블록에서 조용히 삼키고, 빈 결과이면 연관 작품 섹션 자체를 렌더링하지 않는다.

시드 데이터에는 12개 핀 모두 태그가 할당되어 있으나, 태그는 선택 사항이므로 태그 없는 핀은 실제로 존재할 수 있다. spec.md의 "태그가 없는 작품의 연관 작품" 시나리오는 방어적 프로그래밍이 아니라 실제 발생하는 케이스이므로 반드시 처리해야 한다. 또한 태그가 있어도 매칭 결과가 부족한 경우는 빈번히 발생할 수 있다.

> **NOTE**: 현재 핀 생성 핸들러(`apps/api/internal/pin/handler.go`)는 태그 0개를 거부하는 검증이 남아 있다(`"태그는 1개 이상 선택해야 합니다"`). 태그 선택 정책과 일치하도록 이 검증을 제거하거나 완화해야 한다.

## Goals / Non-Goals

**Goals:**
- 태그 매칭 결과가 부족할 때 다단계 fallback으로 연관 핀을 채운다
- 연관 핀 응답이 항상 유의미한 결과를 포함하도록 한다
- 프론트엔드에서 API 에러를 로깅한다

**Non-Goals:**
- ML 기반 추천 도입 (Phase 3 범위)
- 연관 핀 개수 상한(10개) 변경
- 연관 핀 API의 페이지네이션 지원
- 시드 데이터 수정 (현재 태그가 이미 할당되어 있음)

## Decisions

### 1. 다단계 fallback 전략

태그 매칭 결과가 10개 미만일 때, 남은 슬롯을 채우는 fallback 쿼리를 순차 실행한다.

- **1단계**: 태그 일치도 기반 (기존 쿼리) — 태그가 겹치는 핀을 일치도순으로
- **2단계**: 같은 미디어 타입 — 태그 매칭 결과가 부족하면 같은 미디어 타입의 최신 핀으로 채움
- **3단계**: 최신 핀 — 그래도 부족하면 미디어 타입 무관하게 최신 핀으로 채움

**대안 고려:**
- 단일 UNION ALL 쿼리: PostgreSQL 최적화가 어렵고 디버깅이 복잡해진다. 개별 쿼리가 명확하다.
- 같은 크리에이터 fallback: 자기 큐레이션 순환이 발생할 수 있어 제외.

### 2. 핸들러에서 fallback 조합

DB 레이어에 새로운 쿼리 2개를 추가하고, 핸들러에서 결과를 조합한다. 이미 반환된 핀 ID를 제외하며 최대 10개를 채운다.

### 3. 프론트엔드 에러 로깅

silent catch를 console.error로 교체한다. 서버 컴포넌트이므로 서버 로그에 기록된다.

## Risks / Trade-offs

- [추가 쿼리로 인한 지연] → fallback은 1단계 결과가 부족할 때만 실행되므로 대부분의 경우 기존과 동일한 성능. 최악의 경우에도 3개의 단순 쿼리.
- [중복 핀 제외 로직의 복잡성] → 핸들러에서 이미 반환된 핀 ID 집합을 관리. 로직은 단순하며 테스트 가능.
- [fallback 결과의 연관성 저하] → 태그 매칭이 없을 때 같은 미디어 타입이라도 보여주는 것이 빈 결과보다 사용자 경험이 낫다.
