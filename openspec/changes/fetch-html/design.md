## 배경

Pioneer 크롤러에 "not implemented"를 반환하는 `fetchHTML()` 스텁 메서드가 있습니다. 이로 인해 BFS 크롤 루프가 모든 URL을 조용히 건너뜁니다 (pioneer.go 100-102줄에서 fetch 에러 시 그냥 `continue`). 실제 그래프 구축을 위해서는 프로덕션용 HTTP 클라이언트가 필요합니다.

현재 상태:
- Pioneer.Run()이 빈 큐를 만들고, 한 번 루프를 돌고, fetchHTML 스텁을 만나고, continue하고, 종료됨
- DB에 유효한 사이트가 있음에도 노드가 하나도 생성되지 않음
- 현재 외부 HTTP 라이브러리 의존성 없음

## 목표 / 비목표

**목표:**
- Pioneer에서 동작하는 HTTP fetch 구현
- 타임아웃, 리다이렉트, 일반적인 에러 우아하게 처리
- 크롤이 실제로 그래프 노드를 구축하게 만들기
- Go 표준 라이브러리 (net/http)만 사용

**비목표:**
- JavaScript 렌더링 (초기 크롤에 불필요)
- 쿠키/세션 처리 (stateless 크롤)
- 재시도 로직 (Pioneer 루프가 상위 레벨에서 처리)
- 프록시 지원 (나중에 필요하면 추가)

## 결정 사항

### 결정 1: 표준 라이브러리 net/http와 커스텀 Transport 사용
**근거**: 외부 의존성 불필요 (colly, goquery). 단순히 raw HTML fetching만 필요. 커스텀 Transport로 타임아웃, 리다이렉트를 세밀하게 제어 가능.

**고려한 대안**:
- Colly 프레임워크: 너무 무거움, 원하지 않는 캐싱/상태 관리를 가져옴
- go-resty: 더 간단한 API지만 기본 GET 요청에 또 다른 의존성 추가

### 결정 2: 10초 타임아웃, 최대 5번 리다이렉트
**근거**: 
- 10초는 느린 사이트와 무한 대기하지 않기의 균형점
- 5번 리다이렉트는 일반적인 리다이렉트 체인 (http→https→www) 처리하면서 무한 루프 방지

**고려한 대안**:
- 30초 타임아웃: rate limiting 있는 BFS에는 너무 느림
- 리다이렉트 제한 없음: 리다이렉트 루프 위험

### 결정 3: 4xx/5xx 시 에러 반환, 호출자가 결정하게
**근거**: Pioneer 루프에 이미 에러 처리 로직이 있음 (100-102줄). HTTP 레이어는 단순하게 유지하고, 비즈니스 로직이 404 vs 500 처리 방법 결정.

**고려한 대안**:
- 5xx만 에러로: 하지만 404는 URL이 죽었다는 의미, 건너뛰어야 함
- 404를 빈 본문과 함께 성공으로 처리: 오해의 소지, 명시적으로 하는 게 나음

### 결정 4: 최소한의 User-Agent (스푸핑 안 함)
**근거**: 정직한 봇 식별. "FugueBot/1.0 (+https://fugue.app)"으로 사이트가 필요하면 차단할 수 있게.

## 위험 요소 / 트레이드오프

**[위험]** 사이트가 우리 User-Agent를 차단  
→ **완화**: 필요하면 나중에 UA 설정 추가, 일단 정직하게 시작

**[위험]** 큰 HTML 응답이 메모리 소비  
→ **완화**: MVP에서는 수용 (Pioneer는 listing/detail 페이지 대상, 일반적으로 <500KB). 필요시 나중에 io.LimitReader(resp.Body, 5MB) 추가 가능.

**[위험]** 타임아웃이 느린 사이트에 너무 짧을 수 있음  
→ **완화**: 초기 페이지에는 10초가 합리적, 나중에 설정 가능하게 만들 수 있음

**[트레이드오프]** fetchHTML에 재시도 로직 없음  
→ 수용: Pioneer 루프가 나중에 전체 노드를 재시도 가능, 관심사 분리가 더 단순
