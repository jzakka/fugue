## Purpose

핀을 묶는 보드의 생성·조회·수정·삭제와 보드-핀 관계, 그리고 유저의 보드 목록(본인/타인 가시성 포함)을 제공한다.
## Requirements
### Requirement: 보드를 생성한다
시스템은 인증된 유저가 핀을 묶는 보드를 생성할 수 있어야 한다(SHALL).

#### Scenario: 보드 생성
- **WHEN** 인증된 유저가 보드 이름을 포함하여 생성을 요청하면
- **THEN** 보드가 생성되고 기본 공개 상태로 설정된다

#### Scenario: 보드 이름은 필수이다
- **WHEN** 이름 없이 보드 생성을 요청하면
- **THEN** 유효성 검사 오류가 반환된다

---

### Requirement: 보드를 조회한다
시스템은 보드의 상세 정보와 포함된 핀 목록을 제공해야 한다(SHALL).

#### Scenario: 공개 보드 조회
- **WHEN** 누구나 공개 보드를 조회하면
- **THEN** 보드 정보와 핀 목록이 반환된다

#### Scenario: 비공개 보드는 소유자만 조회
- **WHEN** 소유자가 아닌 유저가 비공개 보드를 조회하면
- **THEN** 보드를 찾을 수 없다는 응답이 반환된다

#### Scenario: 소유자는 비공개 보드 조회 가능
- **WHEN** 소유자가 자신의 비공개 보드를 조회하면
- **THEN** 보드 정보와 핀 목록이 반환된다

---

### Requirement: 보드를 수정한다
시스템은 보드 소유자만 보드를 수정할 수 있어야 한다(SHALL).

#### Scenario: 소유자가 보드 이름 수정
- **WHEN** 소유자가 보드 이름 변경을 요청하면
- **THEN** 보드 이름이 업데이트된다

#### Scenario: 소유자가 공개 여부 변경
- **WHEN** 소유자가 보드의 공개 설정을 변경하면
- **THEN** 공개 여부가 업데이트된다

#### Scenario: 소유자가 아니면 수정 불가
- **WHEN** 소유자가 아닌 유저가 보드 수정을 요청하면
- **THEN** 권한 오류가 반환된다

#### Scenario: 수정 후 보드 정보 조회가 실패한 경우
- **WHEN** 보드 수정 자체는 성공했으나 응답 조립을 위한 보드 정보(`pin_count`/`cover_images`) 조회가 결정적으로 실패한 경우
- **THEN** 서버는 잘못된 값(예: 0/빈 목록)을 응답하지 않고 에러를 반환한다 (응답 정확성을 묵시 zero value로 우회하지 않도록 fail-closed)

---

### Requirement: 보드를 삭제한다
시스템은 보드 소유자만 보드를 삭제할 수 있어야 한다(SHALL).

#### Scenario: 소유자가 보드 삭제
- **WHEN** 소유자가 보드 삭제를 요청하면
- **THEN** 보드와 보드-핀 관계가 삭제된다 (핀 자체는 삭제되지 않는다)

---

### Requirement: 보드에 핀을 추가/제거한다
시스템은 보드 소유자가 자신의 보드에 핀을 추가하거나 제거할 수 있어야 한다(SHALL). 존재하지 않는 핀을 추가하려는 요청은 서버 오류가 아니라 찾을 수 없음 오류로 거절해야 한다(SHALL).

#### Scenario: 보드에 핀 추가
- **WHEN** 소유자가 보드에 핀 추가를 요청하면
- **THEN** 핀이 보드에 추가된다

#### Scenario: 같은 핀 중복 추가 방지
- **WHEN** 이미 보드에 있는 핀을 다시 추가 요청하면
- **THEN** 중복 추가 오류가 반환된다

#### Scenario: 하나의 핀이 여러 보드에 속할 수 있다
- **WHEN** 동일한 핀을 서로 다른 보드에 추가하면
- **THEN** 두 보드 모두에서 해당 핀이 표시된다

#### Scenario: 존재하지 않는 핀 추가는 찾을 수 없음 오류로 거절된다
- **WHEN** 소유자가 존재하지 않는 핀 ID로 보드에 핀 추가를 요청하면
- **THEN** 서버 오류가 아니라 찾을 수 없음 오류가 반환된다

#### Scenario: 보드에서 핀 제거
- **WHEN** 소유자가 보드에서 핀 제거를 요청하면
- **THEN** 보드-핀 관계가 삭제된다 (핀 자체는 유지된다)

---

### Requirement: 유저의 보드 목록을 조회한다
시스템은 유저의 보드 목록을 제공해야 한다(SHALL).

#### Scenario: 본인의 보드 목록
- **WHEN** 인증된 유저가 자신의 보드 목록을 조회하면
- **THEN** 공개 + 비공개 모든 보드가 반환된다

#### Scenario: 타인의 보드 목록
- **WHEN** 다른 유저의 보드 목록을 조회하면
- **THEN** 공개 보드만 반환된다

#### Scenario: 목록 내 보조 정보 조회가 실패한 경우
- **WHEN** 보드 목록 안의 한 보드에 대한 보조 정보(`pin_count`/`cover_images`) 조회가 결정적으로 실패한 경우
- **THEN** 서버는 해당 보드만 잘못된 값으로 표시한 부분 응답을 반환하지 않고 에러를 반환한다 (목록 가용성을 잘못된 값으로 우회하지 않도록 fail-closed)

### Requirement: 공개 보드 조회 라우트는 선택적 인증 미들웨어로 보호된다

production 서버 라우터의 보드 단건 조회 엔드포인트(`GET /api/boards/{id}`)와 보드 목록 조회 엔드포인트(`GET /api/boards`)는 선택적 인증 미들웨어를 통해 핸들러에 도달해야 한다(SHALL). 인증 토큰이 존재하면 그 토큰의 유저 식별자가 핸들러에 노출되어야 한다(SHALL). 토큰이 부재하거나 유효하지 않으면 핸들러가 비인증 호출자에 대한 분기를 수행하도록 빈 인증 컨텍스트로 진입해야 한다(SHALL). 두 라우트가 토큰 부재만으로 401을 반환해서는 안 된다(SHALL NOT).

본 Requirement는 기존 Requirement `보드를 조회한다`와 `유저의 보드 목록을 조회한다`가 production에서 enforce되도록 보장하는 wiring 계약이다. 기존 Requirement의 행위 정의(비공개 보드 소유자 분기, 본인/타인 목록 분기)는 변경하지 않는다.

#### Scenario: 소유자가 비공개 보드를 인증 토큰을 제시하며 단건 조회

- **WHEN** 비공개 보드의 소유자가 인증 토큰을 제시하며 그 보드를 단건 조회하면
- **THEN** 핸들러는 호출자의 유저 식별자로 분기 가능한 상태에서 호출되어, 기존 Requirement `보드를 조회한다`의 "소유자는 비공개 보드 조회 가능" Scenario에 정의된 응답을 반환한다

#### Scenario: 비소유자가 비공개 보드를 단건 조회

- **WHEN** 비공개 보드의 비소유자(또는 비인증 호출자)가 그 보드를 단건 조회하면
- **THEN** 핸들러는 비인증 또는 비일치 분기를 수행하며, 기존 Requirement `보드를 조회한다`의 "비공개 보드는 소유자만 조회" Scenario에 정의된 응답을 반환한다. 401은 반환되지 않는다

#### Scenario: 본인이 자신의 보드 목록을 인증 토큰을 제시하며 조회

- **WHEN** 인증 토큰을 제시한 호출자가 자신의 `creator_id`로 보드 목록을 조회하면
- **THEN** 핸들러는 호출자가 본인임을 식별 가능한 상태에서 호출되어, 기존 Requirement `유저의 보드 목록을 조회한다`의 "본인의 보드 목록" Scenario에 정의된 응답을 반환한다

#### Scenario: 타인의 보드 목록 또는 비인증 호출자의 보드 목록

- **WHEN** 인증 토큰이 없거나 자신과 다른 `creator_id`로 보드 목록을 조회하면
- **THEN** 핸들러는 비인증/비본인 분기를 수행하며, 기존 Requirement `유저의 보드 목록을 조회한다`의 "타인의 보드 목록" Scenario에 정의된 응답을 반환한다. 401은 반환되지 않는다

#### Scenario: 유효하지 않은 토큰을 가진 두 라우트 요청

- **WHEN** 만료·서명 불일치·식별자 파싱 실패 중 어느 사유로든 유효하지 않은 토큰을 제시한 호출자가 두 라우트 중 하나를 호출하면
- **THEN** 핸들러는 비인증 분기를 수행한다. 401은 반환되지 않는다

### Requirement: 보드 상세의 추가 로드 컨트롤은 동일 역할 컨트롤과 일관된 시각 표현을 가진다

보드 상세 페이지에서 추가 핀을 수동으로 불러오는 컨트롤("더보기")은, 서비스 내 동일 역할의 수동 추가-로드 컨트롤(검색 결과의 "더보기")과 동일한 시각 표현(채움·크기 위계)으로 렌더되어야 한다(SHALL). 컨트롤의 동작(클릭 시 다음 페이지 로드, 로딩 중 비활성화와 진행 표시, 더 불러올 항목이 없으면 미표시)은 변경되지 않아야 한다(SHALL).

#### Scenario: 보드 상세와 검색 결과의 더보기 컨트롤 시각 일치

- **WHEN** 사용자가 핀이 한 페이지를 초과하는 보드 상세 페이지와 결과가 한 페이지를 초과하는 검색 결과 페이지를 각각 열면
- **THEN** 두 페이지의 "더보기" 컨트롤은 동일한 채움과 크기 위계로 렌더된다

#### Scenario: 더보기 컨트롤의 기존 동작 유지

- **WHEN** 사용자가 보드 상세의 "더보기" 컨트롤을 클릭하면
- **THEN** 다음 페이지의 핀이 목록에 추가되고, 로딩 중에는 컨트롤이 비활성화되며 진행 표시가 나타나고, 더 불러올 핀이 없으면 컨트롤이 표시되지 않는다


### Requirement: 보드 핀 추가 실패 피드백은 서비스 공통 실패 안내 문형을 따른다

보드에 핀 추가가 서버 오류 등으로 실패했을 때 사용자에게 보이는 안내 문구는, 서비스 전반의 작업 실패 안내가 사용하는 공통 문형(대상 작업을 명사구로 제시하고 실패 사실을 알리는 형태, 합쇼체)을 따라야 하며(SHALL), 동일 피드백 영역에 표시되는 다른 실패 안내(보드 생성 실패 등)와 문형이 일치해야 한다(SHALL). 별도의 재시도 유도 문구는 덧붙이지 않는다.

#### Scenario: 보드 핀 추가 실패 안내

- **WHEN** 사용자가 보드에 핀 추가를 시도했으나 중복 이외의 사유로 실패하면
- **THEN** 실패 안내 문구가 서비스 공통 실패 안내 문형(합쇼체, 대상 작업 명사구 + 실패 고지)으로만 표시되고 재시도 유도 문구는 포함되지 않는다

#### Scenario: 중복 추가 안내는 별도 문구를 유지한다

- **WHEN** 이미 보드에 있는 핀을 다시 추가하여 중복 오류가 반환되면
- **THEN** 중복 상황을 설명하는 별도 안내 문구가 표시되며 공통 실패 문형으로 대체되지 않는다

#### Scenario: 동일 모달 내 실패 안내 문형 일치

- **WHEN** 보드에 추가 모달에서 보드 추가 실패 안내와 보드 생성 실패 안내가 각각 표시되면
- **THEN** 두 안내는 동일한 문형(무접미 사실 서술형)을 사용한다

### Requirement: 보드 추가 성공 안내의 보드명 인용 표기는 서비스 가시 카피 인용 표기를 따른다

보드에 핀 추가 성공 안내에서 보드 이름을 인용부호로 감싸 표시할 때, 서비스의 다른 가시 카피(검색 결과 헤딩, 빈 검색 결과 안내 등)가 동적 이름 인용에 사용하는 곡선따옴표(“ ”)와 동일한 인용 표기를 사용해야 한다(SHALL).

#### Scenario: 보드 추가 성공 안내의 보드명 인용

- **WHEN** 사용자가 보드에 핀을 추가하는 데 성공하여 보드명이 포함된 성공 안내가 표시되면
- **THEN** 보드명은 곡선따옴표(“ ”)로 감싸져 표시된다

#### Scenario: 검색 표면의 인용 표기와 일치

- **WHEN** 검색 결과 헤딩·빈 검색 결과 안내와 보드 추가 성공 안내가 각각 동적 이름을 인용 표시하면
- **THEN** 세 표면 모두 동일한 곡선따옴표 표기를 사용한다

### Requirement: 보드 생성 폼의 취소 버튼은 생성 요청 진행 중 비활성화된다

보드 생성 폼(마이페이지 새 보드 폼, 핀 상세 보드에 추가 모달의 새 보드 폼)의 취소 버튼은 보드 생성 요청이 진행 중인 동안 SHALL 비활성화되고 비활성 상태가 시각적으로 구분되어야 하며, 요청이 진행 중이 아닐 때 취소를 누르면 SHALL 폼이 닫히고 입력이 초기화되어야 한다.

#### Scenario: 생성 요청 진행 중 취소 불가

- WHEN 사용자가 새 보드 이름을 입력하고 생성을 눌러 보드 생성 요청이 진행 중일 때
- THEN 취소 버튼은 비활성화되어 눌리지 않고, 비활성 상태가 시각적으로 흐리게 표시된다

#### Scenario: 유휴 상태에서 취소 정상 동작

- WHEN 보드 생성 요청이 진행 중이 아닐 때 사용자가 취소를 누르면
- THEN 새 보드 폼이 닫히고 입력한 보드 이름이 초기화된다

### Requirement: 보드 생성 폼 열기 트리거의 추가 기호는 장식 처리된다

마이페이지 보드 섹션의 보드 생성 폼 열기 트리거는 추가(add)를 나타내는 기호를 시각적으로 표시하되, 그 기호는 보조기술에 노출되는 접근 가능한 이름(accessible name)에 포함되지 않아야 한다(SHALL). 접근 가능한 이름은 동작 명칭("새 보드")만으로 구성되어야 한다(SHALL).

#### Scenario: 스크린리더가 보드 생성 폼 열기 트리거를 읽는다

- WHEN 보조기술 사용자가 마이페이지 보드 섹션의 보드 생성 폼 열기 트리거에 도달하면
- THEN 트리거의 접근 가능한 이름은 "새 보드"로 발화되며 추가 기호("플러스" 등)는 발화되지 않는다

#### Scenario: 폼 열기/닫기 토글 동작이 유지된다

- WHEN 사용자가 보드 생성 폼 열기 트리거를 클릭하면
- THEN 보드 생성 폼이 열리고, 트리거의 펼침 상태 표시(aria-expanded)가 폼 표시 여부와 동기화된다

### Requirement: 보드 편집 폼은 Enter 키로 저장을 실행한다

보드 상세 화면의 보드 편집 폼에서 사용자가 이름 입력 또는 설명 입력에 포커스를 둔 채 Enter 키를 누르면, 시스템은 SHALL 저장 버튼을 누른 것과 동일하게 보드 수정 저장을 실행한다.

#### Scenario: 이름 입력에서 Enter로 저장

- **WHEN** 사용자가 보드 편집 폼의 이름 입력에 유효한 이름을 입력하고 Enter 키를 누르면
- **THEN** 보드 수정 저장이 실행되고 성공 시 편집 모드가 종료되며 변경된 이름이 반영된다

#### Scenario: 설명 입력에서 Enter로 저장

- **WHEN** 사용자가 보드 편집 폼의 설명 입력에 포커스를 두고 Enter 키를 누르면
- **THEN** 보드 수정 저장이 실행된다

#### Scenario: 빈 이름으로 Enter 시 검증 에러

- **WHEN** 사용자가 이름 입력을 비운 채 Enter 키를 누르면
- **THEN** 저장 버튼 클릭과 동일하게 이름 필수 검증 에러가 표시되고 편집 모드가 유지된다

### Requirement: 보드 커버 이미지 로드 실패 시 깨진 이미지 표시를 노출하지 않는다

보드 커버 콜라주 및 미니커버의 개별 이미지가 로드에 실패하면, 화면은 브라우저의 깨진 이미지 아이콘을 노출하지 않고 해당 이미지를 숨겨 슬롯 배경으로 degrade해야 한다(SHALL). 이는 커버 이미지가 4장 미만일 때의 빈 슬롯 표시와 동일한 시각 처리다.

#### Scenario: 커버 콜라주 슬롯 이미지 로드 실패

- **WHEN** 보드 커버 콜라주의 한 슬롯 이미지가 로드에 실패하면
- **THEN** 깨진 이미지 아이콘 없이 해당 슬롯이 빈 슬롯과 동일한 배경으로 표시되고, 나머지 슬롯은 정상 표시된다

#### Scenario: 보드 선택 모달 미니커버 로드 실패

- **WHEN** 핀 상세의 보드 선택 목록에서 보드 미니커버 이미지가 로드에 실패하면
- **THEN** 깨진 이미지 아이콘 없이 미니커버가 숨겨지고, 보드 이름·핀 수 등 항목 정보와 선택 동작은 유지된다

#### Scenario: 정상 URL 렌더 불변

- **WHEN** 보드 커버 이미지가 정상적으로 로드되면
- **THEN** 기존과 동일한 콜라주/미니커버 레이아웃으로 표시된다
