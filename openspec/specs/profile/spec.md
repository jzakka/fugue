## Purpose

유저의 공개 프로필 조회와 본인 프로필 수정 기능을 제공한다. 프로필은 단순 계정이며 포트폴리오 기능은 없다.
## Requirements
### Requirement: 유저 프로필을 조회한다
시스템은 유저의 공개 프로필을 제공해야 한다(SHALL). 프로필은 단순 계정이며, 포트폴리오 기능은 없다.

#### Scenario: 공개 프로필 조회
- **WHEN** 유저 ID로 프로필을 조회하면
- **THEN** 닉네임, 아바타, 보드 목록, 핀 목록이 반환된다

#### Scenario: 존재하지 않는 유저
- **WHEN** 존재하지 않는 유저 ID로 조회하면
- **THEN** 404 응답이 반환된다

### Requirement: 본인 프로필을 수정한다
시스템은 인증된 유저가 자신의 닉네임과 아바타를 수정할 수 있어야 한다(SHALL).

#### Scenario: 닉네임 수정
- **WHEN** 인증된 유저가 닉네임 변경을 요청하면
- **THEN** 닉네임이 업데이트된다

#### Scenario: 닉네임은 필수이다
- **WHEN** 빈 닉네임으로 수정을 요청하면
- **THEN** 유효성 검사 오류가 반환된다

#### Scenario: 아바타 수정
- **WHEN** 인증된 유저가 아바타 URL 변경을 요청하면
- **THEN** 아바타가 업데이트된다

### Requirement: 공개 프로필 조회 응답에 보드 요약과 핀 요약을 포함한다

시스템은 공개 프로필 조회 응답 페이로드에 그 유저의 공개 보드 요약 목록과 최근 핀 요약 목록 두 가지를 항상 포함해야 한다(SHALL). 두 목록은 각각 별개의 응답 키로 노출되어야 하며, 한쪽이 빈 경우에도 빈 배열이 응답에 존재해야 한다(SHALL).

공개 보드 요약 목록은 해당 유저의 공개 보드만 포함해야 하며, 호출자의 인증 여부와 무관하게 비공개 보드가 본 응답에 노출되어서는 안 된다(SHALL NOT). 본인이 본인의 프로필을 조회하더라도 본 응답에는 공개 보드만 포함된다. 비공개 보드는 기존 보드 라우트(`GET /api/boards?creator_id=...`)가 본인 분기에서 책임진다.

두 목록은 페이지네이션 메타데이터를 가지지 않으며 일정 상한까지의 요약을 반환한다(SHALL). 상한 초과분은 본 응답에 포함되지 않으며 클라이언트는 더 많은 항목을 별도 endpoint(`GET /api/boards?creator_id=...`, `GET /api/pins?creator_id=...`)로 조회한다. 정확한 상한 값은 시스템 운영 디테일이며 본 Requirement는 상한이 존재한다는 사실만 묶는다.

본 Requirement는 기존 Requirement `유저 프로필을 조회한다` Scenario "공개 프로필 조회"의 SHALL("닉네임, 아바타, 보드 목록, 핀 목록이 반환된다")이 production에서 enforce되도록 보장하는 응답 페이로드 계약이다. 기존 Scenario의 의미는 변경하지 않는다.

#### Scenario: 응답 페이로드에 두 요약 키가 함께 포함된다

- **WHEN** 유효한 유저 ID로 `GET /api/creators/{id}`를 호출하면
- **THEN** 응답 본문은 기존 필드(닉네임·아바타)에 더해 `boards`와 `pins` 두 키를 포함한다. 두 키는 각각 공개 보드 요약 배열과 핀 요약 배열이다

#### Scenario: 보드·핀이 없는 유저도 빈 배열을 반환한다

- **WHEN** 보드가 없거나 핀이 없는 유저 ID로 프로필을 조회하면
- **THEN** 빈 쪽 키는 `null`이 아닌 빈 배열로 직렬화되어 응답에 존재한다. 두 키 중 어느 하나도 누락되지 않는다

#### Scenario: 공개 보드만 보드 요약 배열에 포함된다

- **WHEN** 비공개 보드를 가진 유저 ID로 프로필을 조회하면(호출자가 본인이든 타인이든 비인증이든)
- **THEN** 비공개 보드는 `boards` 배열에 포함되지 않는다. 같은 유저의 공개 보드만 포함된다

#### Scenario: 응답은 상한까지의 요약만 반환한다

- **WHEN** 공개 보드 또는 핀 수가 시스템 상한을 초과하는 유저 ID로 프로필을 조회하면
- **THEN** 응답의 `boards`·`pins` 배열 길이는 각 상한 이하이며, 초과분은 응답에 포함되지 않는다. 클라이언트가 더 많은 항목을 보려면 `GET /api/boards?creator_id=...`·`GET /api/pins?creator_id=...`를 별도로 호출한다

#### Scenario: 존재하지 않는 유저는 404이며 두 요약 fetch가 일어나지 않는다

- **WHEN** 존재하지 않는 유저 ID로 프로필을 조회하면
- **THEN** 응답은 404이며 응답 본문은 기존 Scenario "존재하지 않는 유저"가 정의한 404 행위와 동일하다. `boards`·`pins` 두 키는 응답에 존재하지 않는다(404 본문은 본 Requirement의 두 키 형태를 따르지 않는다)

### Requirement: 프로필 미디어타입 필터 칩은 피드 미디어타입 필터와 동일한 선택 시각 어휘를 공유한다

프로필/마이페이지의 미디어타입 필터 칩(토글 버튼)은 선택(활성) 상태를 피드의 미디어타입 필터와 동일한 시각 어휘(반전 강조)로 SHALL 렌더한다. 액센트 색 채움 강조는 태그 선택 role 에 한정되며, 미디어타입 뷰-필터의 선택 강조에 SHALL NOT 사용한다.

#### Scenario: 프로필 필터 칩 선택 시각의 표면 간 동형성

- WHEN 사용자가 프로필 페이지에서 미디어타입 필터 칩을 선택하면
- THEN 선택된 칩은 피드 미디어타입 필터의 선택 칩과 동일한 반전 강조로 렌더되고
- AND 액센트 색 채움은 나타나지 않으며
- AND 비선택 칩의 hover/focus 시각 전이도 피드 미디어타입 필터와 동일한 어휘를 따른다

### Requirement: 공개 프로필 화면은 데이터 로드 중 스켈레톤 로딩 상태를 표시한다

공개 프로필 화면으로 이동하거나 직접 진입할 때, 프로필 데이터가 준비되기 전까지 실제 화면 구조(상단 내비게이션 자리, 프로필 헤더, 작품 그리드)를 본뜬 스켈레톤 자리표시자가 shimmer 모션과 함께 표시되어야 한다(SHALL). 스켈레톤의 형태는 로드 완료 후 실제로 렌더되는 요소들의 크기·배치와 일치해야 하며(SHALL), 실제 요소의 크기가 뷰포트 크기에 따라 달라지는 경우 스켈레톤 자리표시자도 동일한 뷰포트 조건에서 동일하게 크기가 전환되어야 하고(SHALL), 실제 화면에 존재하지 않는 요소의 자리표시자를 포함하지 않아야 한다(SHALL).

#### Scenario: 다른 화면에서 프로필로 이동

- **WHEN** 사용자가 다른 화면에서 크리에이터 프로필 링크를 눌러 이동하면
- **THEN** 서버 데이터 로드가 끝나기 전에 스켈레톤 로딩 화면이 즉시 표시되고, 로드가 완료되면 실제 프로필 콘텐츠로 교체된다

#### Scenario: 스켈레톤과 실제 화면의 구조 일치

- **WHEN** 스켈레톤 로딩 화면이 표시되면
- **THEN** 프로필 헤더 자리표시자는 실제 헤더의 구성(아바타, 닉네임 제목, 핀 개수 행)과 대응하며, 실제 헤더에 없는 요소(소개글·태그류)의 자리표시자는 표시되지 않는다

#### Scenario: 넓은 뷰포트에서 제목 자리표시자의 반응형 크기 일치

- **WHEN** 실제 닉네임 제목의 세로 크기가 커지는 넓은 뷰포트에서 스켈레톤 로딩 화면이 표시되면
- **THEN** 닉네임 제목 자리표시자의 세로 크기도 커진 실제 제목의 줄 높이와 일치하여, 로드 완료 후 실제 콘텐츠로 교체될 때 제목 아래 요소들의 세로 위치가 이동하지 않는다

#### Scenario: 좁은 뷰포트에서 제목 자리표시자 크기 유지

- **WHEN** 좁은 뷰포트에서 스켈레톤 로딩 화면이 표시되면
- **THEN** 닉네임 제목 자리표시자의 세로 크기는 해당 뷰포트의 실제 제목 줄 높이와 일치한다

#### Scenario: 로드 완료 후 최종 화면 불변

- **WHEN** 프로필 데이터 로드가 완료되면
- **THEN** 렌더되는 최종 프로필 화면은 로딩 상태 도입 이전과 동일하다

#### Scenario: 존재하지 않는 크리에이터 진입

- **WHEN** 존재하지 않는 크리에이터의 프로필 주소로 진입하면
- **THEN** 로딩 상태가 잠시 표시될 수 있으나 최종적으로 404 화면이 표시된다

### Requirement: 아바타 이미지 로드 실패 시 깨진 이미지 표시를 노출하지 않는다

유저/크리에이터 아바타 이미지의 URL이 유효하지 않거나 로드에 실패하면, 화면은 브라우저의 깨진 이미지 아이콘을 노출하지 않고 해당 이미지를 숨겨야 한다(SHALL). 인접한 닉네임 등 텍스트 식별 요소는 그대로 유지된다.

#### Scenario: 프로필 헤더 아바타 로드 실패

- **WHEN** 크리에이터 프로필 페이지에서 아바타 이미지 URL이 로드에 실패하면
- **THEN** 깨진 이미지 아이콘 없이 아바타 이미지가 숨겨지고, 닉네임 등 나머지 프로필 정보는 정상 표시된다

#### Scenario: 내비게이션 바 아바타 로드 실패

- **WHEN** 로그인 유저의 내비게이션 바 아바타 이미지가 로드에 실패하면
- **THEN** 깨진 이미지 아이콘 없이 아바타가 숨겨지고, 닉네임 텍스트와 마이페이지 링크 동작은 유지된다

#### Scenario: 정상 URL 렌더 불변

- **WHEN** 아바타 이미지 URL이 정상적으로 로드되면
- **THEN** 기존과 동일한 크기·모양·테두리로 아바타가 표시된다

### Requirement: 공개 프로필 핀 목록은 스크립트 비활성 환경에서 페이지네이션 수단을 제공한다

공개 프로필 화면의 핀 목록은 스크립트 실행이 불가능한 환경에서도 초기 배치 이후의 핀에 접근할 수 있는 수단을 제공해야 한다(SHALL). 이 수단은 스크립트가 활성인 환경에서는 노출되지 않아야 한다(SHALL). 피드 화면이 동일 상황에서 제공하는 페이지네이션 수단과 동일한 시각 표기를 사용해야 한다(SHALL).

#### Scenario: 스크립트 비활성 상태에서 다음 배치로 이동한다

- WHEN 스크립트 실행이 비활성인 브라우저에서 공개 프로필을 열고 추가 핀이 존재하면
- THEN 핀 목록 하단에 다음 배치로 이동하는 링크가 표시되고, 링크를 따라가면 다음 배치의 핀이 서버 렌더로 표시된다

#### Scenario: 스크립트 활성 상태에서는 폴백이 노출되지 않는다

- WHEN 스크립트 실행이 활성인 브라우저에서 공개 프로필을 열면
- THEN 페이지네이션 폴백 링크는 표시되지 않고 기존 자동 추가 로드 동작이 유지된다

#### Scenario: 이동 지점 지정이 없으면 기존과 동일하게 표시된다

- WHEN 이동 지점 지정 없이 공개 프로필을 열면
- THEN 첫 배치의 핀이 기존과 동일하게 표시된다
