Pioneer · Harvester · Scheduler 동작 흐름

Fugue의 콘텐츠 크롤러는 세 개의 독립된 역할로 분리되어 있습니다. 외부 사이트를 탐색하는 탐색자(Pioneer), 콘텐츠를 추출해 Pin으로 적재하는 수확자(Harvester), 그리고 두 일꾼이 다룰 URL의 순서·재시도·속도를 책임지는 스케줄러(Scheduler)입니다. 세 모듈은 직접 호출하지 않고 두 개의 URL 큐(pioneer_frontier / harvester_frontier)를 통해서만 이어집니다.

스케줄러 (Scheduler / URL 큐)

1. 전체 구도 — 두 일꾼, 두 큐

스케줄러는 단순히 "다음에 처리할 URL을 꺼내주는 곳"이 아니라, 큐 자체와 그 큐의 규약을 함께 책임지는 경계입니다. 탐색자와 수확자는 자기 메모리에 어떤 큐도 보관하지 않고, 매 사이클 스케줄러에게 "한 건 줘"라고 요청해서 받은 한 건만 처리합니다.

사이트 구조 탐사 워커
· 한 URL을 받아 페이지 가져오기 · 새로 발견한 링크들 큐에 추가 · 본문 스냅샷을 저장소에 보관 · 같은 URL을 수확자 큐로 넘김

핵심 원칙

탐색자와 수확자는 서로의 존재를 모릅니다. 둘은 같은 코드를 공유하지 않고, 같은 메모리도 공유하지 않습니다. 오직 스케줄러가 들고 있는 두 개의 큐를 통해서만 일감이 흘러갑니다. 덕분에 한쪽 워커가 죽거나 늘어나도 다른 쪽에는 영향이 없고, 같은 종류의 워커를 여러 개 띄워도 큐가 알아서 분배합니다.

2. 역할 분담

탐색자 (Pioneer)

사이트 지도를 그리는 일꾼
  • 읽기탐색자 큐에서 URL 한 건 받기
  • 읽기해당 페이지를 실제로 다운로드
  • 보관받은 본문을 스냅샷 저장소에 업로드
  • 쓰기본문에서 찾은 새 링크를 탐색자 큐에 추가
  • 쓰기원래 URL을 수확자 큐로 전달 (스냅샷 위치 함께)
  • 쓰기스케줄러에 "이 URL 처리 끝났다" 보고

스케줄러 (URL 큐)

일감 분배 · 재시도 · 속도 제어
  • 분배큐에서 가장 우선순위 높은 URL 한 건 잠그고 반환
  • 분배같은 호스트로의 요청은 초당 1건으로 제한
  • 기록처리 중 표시 — 10분간 다른 워커가 못 꺼냄
  • 기록성공 보고 받으면 큐에서 제외
  • 기록실패 종류별로 다음 재시도 시각 계산
  • 기록5번 연속 실패하면 영구 제외 (dead)

수확자 (Harvester)

콘텐츠를 Pin으로 만드는 일꾼
  • 읽기수확자 큐에서 URL 한 건 받기
  • 읽기스냅샷 저장소에서 본문 먼저 시도
  • 읽기스냅샷이 없으면 실시간 HTTP로 재요청
  • 처리본문에서 제목 · 미디어 · 태그 뽑기
  • 처리이미지 · 동영상이 실제 유효한지 검증
  • 쓰기유효하면 Pin 생성 (또는 중복으로 건너뛰기)
  • 쓰기스케줄러에 "이 URL 처리 끝났다" 보고

3. URL 한 건이 흘러가는 길

하나의 URL이 새로 발견되어 최종적으로 Pin이 되기까지의 시퀀스입니다. 세 모듈이 어떻게 한 번씩 손을 댔다 놓는지를 보여줍니다.

P
탐색자가 한 URL을 처리하는 사이클
한 워커는 100건을 처리한 뒤 종료하고, 운영자가 다시 띄웁니다.
1
스케줄러에 "탐색용 URL 한 건 줘" 요청
큐가 비어 있으면 1초 후 다시 시도. 호스트별 속도 제한에 걸리면 다른 호스트의 URL을 우선 분배.
2
받은 URL의 페이지를 실제로 다운로드
10초 타임아웃, 최대 5MB, 리다이렉트 5번까지 허용.
3
받은 본문을 그대로 스냅샷 저장소에 업로드
키 패턴은 "URL 해시 + UTC 날짜". gzip 압축하여 보관. 같은 날 다시 받으면 덮어씀.
4
본문에서 발견한 새 링크를 탐색자 큐에 추가
같은 사이트 · 허용 규칙을 통과한 링크만. 이미 큐에 있는 링크는 자동으로 무시됨.
5
원래 URL을 수확자 큐로 넘김 (스냅샷 위치 동봉)
수확자는 이 정보 덕에 같은 페이지를 다시 다운로드하지 않고 저장된 본문을 재사용할 수 있음.
6
스케줄러에 "이 URL은 fetched 완료" 보고
스케줄러는 이 URL의 실패 카운터를 0으로 리셋하고 큐의 활성 목록에서 제외.
H
수확자가 한 URL을 처리하는 사이클
탐색자가 넘긴 URL을 받아 실제 Pin으로 만드는 단계.
1
스케줄러에 "수확용 URL 한 건 줘" 요청
탐색자 큐와는 다른 별도 큐에서 꺼냄. 두 큐는 서로 독립적으로 우선순위가 매겨짐.
2
먼저 스냅샷 저장소에서 본문을 찾음
탐색자가 같은 날 저장해 둔 본문이 있으면 이걸 사용 → 외부 사이트에 부담 없음.
2a
스냅샷이 없거나 손상됐으면 실시간 HTTP로 재요청
이 경우의 실패 사유는 스케줄러에 노출되지 않음 — "스냅샷 미스"는 운영 로그에만 남음.
3
사이트별 어댑터 또는 범용 추출기로 콘텐츠 뽑기
제목, 본문, 썸네일, 미디어 후보(이미지/오디오/비디오), OG 메타데이터 등.
4
미디어 후보가 진짜로 유효한지 검증
1×1 placeholder 이미지, 너무 짧은 비디오 등은 걸러냄. 살아남은 후보로 Pin 적격성을 판정.
5
적격하면 Pin 생성 (혹은 이미 있으면 중복 처리)
미디어 파일은 S3에 업로드, 메타데이터는 DB에 저장, 태그 자동 매칭.
6
스케줄러에 "이 URL은 harvested 완료, 생성된 Pin 목록 첨부" 보고
한 트랜잭션 안에서 큐 상태 갱신 + URL↔Pin 연결 테이블 기록이 함께 이루어짐.

4. 두 큐 사이의 fanout

같은 URL을 두 번 다루는 것이 아닙니다. 탐색자는 자기가 처리한 URL을 다른 큐로 넘겨 수확자가 이어받게 합니다. 이걸 fanout이라고 부릅니다.

탐색자 워커
N개 인스턴스
→
pioneer_frontier
탐색 대기 URL · 우선순위 높은 순으로 분배
→
탐색자 워커
같은 큐를 공유
↓ 탐색 성공 시 같은 URL을 아래 큐로 넘김 (스냅샷 위치와 함께)
수확자 워커
N개 인스턴스
→
harvester_frontier
수확 대기 URL · 스냅샷 키 포함
→
수확자 워커
같은 큐를 공유

탐색자 큐로 들어가는 새 링크는 중복이면 자동으로 무시됩니다. 수확자 큐로 들어갈 때는 "이미 수확 완료된 URL"은 건드리지 않고, 아직 처리 전이라면 스냅샷 위치와 다음 시도 시각만 갱신됩니다.

5. 스케줄러가 일감을 나눠주는 방식

스케줄러는 단순히 "큐에서 하나 빼서 주기"가 아닙니다. 같은 URL이 두 워커에게 동시에 가지 않도록, 그리고 외부 사이트가 우리 트래픽 때문에 막히지 않도록 두 가지 규약을 같이 적용합니다.

S
한 건의 URL을 분배할 때
워커가 "한 건 줘"를 호출했을 때 내부에서 일어나는 일
1
우선순위가 높고 재시도 시각이 지난 URL 후보 N개 골라보기
DB 안에서 같은 행을 다른 트랜잭션이 들고 있으면 건너뜀 — 동시에 두 워커가 같은 URL을 잡을 수 없음.
2
후보별로 호스트 토큰 검사
호스트별로 "초당 몇 건까지 허용"을 따져, 토큰이 남은 첫 후보를 선택. 모두 막히면 1초 쉬고 재시도.
3
선택된 URL에 10분짜리 처리 중 표시
"다음 시도 시각"을 현재 시각 + 10분으로 밀어두기. 워커가 죽어도 10분 뒤 자연히 다른 워커가 다시 잡아감.
4
URL 문자열을 워커에게 반환
워커가 이걸 받아 자기 파이프라인을 돌림.

6. 실패와 재시도 정책

워커가 어떤 이유로 처리에 실패하면, 어떤 종류의 실패인지를 함께 보고합니다. 스케줄러는 종류에 따라 다음 시도 시각을 다르게 잡습니다.

실패 종류 예시 스케줄러의 대응
http_4xx 404, 410, 401, 403 즉시 실패 카운터 5로 올림 → 다시는 꺼내지 않음 (재시도 불가능한 상태로 판단)
http_5xx 500, 502, 503 카운터 +1, 30초 → 1분 → 2분 → 4분 → 8분 순으로 지수 backoff 후 재시도
network DNS 실패, 연결 끊김, 본문 없음 위와 동일한 지수 backoff 적용
timeout 10초 안에 응답 없음, ctx 취소 위와 동일한 지수 backoff 적용

지수 backoff에는 ±10% 무작위 흔들기(jitter)가 더해집니다. 동시에 많은 URL이 같은 시각에 재시도되어 외부 사이트를 다시 두드리는 "thundering herd"를 방지하기 위해서입니다. 5번 연속 실패하면 그 URL은 영구 제외(dead)되며, 되살리려면 운영자가 직접 DB에서 카운터를 0으로 되돌려야 합니다.

7. 왜 이렇게 갈라놓았나

설계 결정 — 큐 분리

탐색은 무겁고(전체 사이트 BFS) 자주 안 돌아도 되며, 수확은 가볍고 자주 돌아야 합니다. 두 작업의 리듬이 다르므로 같은 큐에 섞으면 한쪽이 다른 쪽을 굶깁니다. 그래서 탐색 대기 URL과 수확 대기 URL을 따로 보관하고, 각자의 워커 풀이 자기 큐만 신경 쓰게 했습니다.

설계 결정 — 스냅샷 우선

탐색자가 이미 받아온 본문을 수확자가 다시 받지 않도록, 받은 본문을 그대로 객체 저장소에 보관합니다. 수확자는 항상 저장소를 먼저 보고, 거기에 없을 때만 실시간 HTTP로 가져옵니다. 그 결과 외부 사이트로의 요청 수가 절반 가까이 줄고, 같은 URL의 추출 결과가 시점에 따라 흔들리는 일도 줄어듭니다.

설계 결정 — 메모리에 큐를 두지 않음

예전 버전은 탐색자 안에 in-memory BFS 큐를 들고 있어서, 워커가 죽으면 그동안 발견한 링크가 모두 휘발됐습니다. 지금은 큐가 Postgres에 있으므로 워커가 죽어도 진행 상태가 그대로 남고, 같은 큐를 여러 워커가 동시에 빨아 쓸 수 있습니다. 워커 한 대는 100건만 처리하고 스스로 종료해, 메모리 누수나 누적 상태 문제를 원천적으로 피합니다.
